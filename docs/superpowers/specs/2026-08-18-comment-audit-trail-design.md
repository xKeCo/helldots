# Comment audit trail, persisted identity and resolution history — design

Date: 2026-08-18
Status: approved, ready for implementation

Three requirements share one mechanism, so they ship as one chunk:

- **Identity from the integrator** — take the session user's stable id and
  display name from the host and attribute comments and replies to it,
  without HellDots managing authentication of its own.
- **Audit history** — show who created, changed or resolved each comment,
  and when.
- **Resolution time** — recalculated over the most recent resolution when a
  comment is reopened, with the earlier resolutions kept.

The third is not built separately. A log of status moves already contains
every resolution a comment has had; building both would mean two records
competing to describe the same fact, two serialization paths and two
validators on the load path.

## Problem

`setCommentStatus` stamps `resolvedAt` on entering `resolved` and clears it
on leaving, so the badge always shows the current resolution and nothing
else. That was deliberate — `DECISIONS.md`, "A single `resolvedAt` instead of
a status history": _"A full `statusHistory` offered more analytical value
than the requirement asked for, at the cost of more payload per comment."_

The requirement now asks for it. This spec reverses that call, and the entry
recording the reversal amends the old one rather than replacing it, per the
repo's rule for a living decision log.

The identity half is closer to done than it looks. `user?: { name, id? }`
already exists, `actorKeyOf` already resolves `user.id ?? user.name ??
anonymous` in one place, and both creation paths already stamp
`this.options.user?.name` as the author. What is missing is that the id is
never persisted: `author` is a display name, so two teammates who share one
cannot be told apart in a record that claims to say _who_.

## Measured cost

A draft of this exact shape — the module, the timeline component, the
normalizer, the serializer, the recording call sites, `authorId` on both
creation paths, nine i18n keys in both locales and the CSS block — was
bundled against `src/index.js` with the real build options, including the
CSS-in-template minifier:

|              | raw          | gzip         |
| ------------ | ------------ | ------------ |
| baseline     | 128.29 KB    | 34.95 KB     |
| with the log | 135.15 KB    | 37.12 KB     |
| delta        | **+6.87 KB** | **+2.16 KB** |

That leaves **12.88 KB of the 50 KB budget**, which the metrics dashboard and
the exporters have to fit into afterwards. No new runtime dependency: the log
is plain objects and the timeline is the same `document.createElement` idiom
as every other component here.

Payload per comment is the other half of the cost, and it lands well inside
the quota strategy `storage.js` already has:

|                                             | bytes     |
| ------------------------------------------- | --------- |
| one audit entry                             | ~150      |
| a typical comment's whole log (3–5 entries) | ~450–750  |
| 100 comments' logs                          | ~45–75 KB |
| one `contextScreenshot`                     | ~33 KB    |

A hundred comments' worth of history costs about what two automatic
screenshots cost. Against a ~5 MB quota that needs no cap, and the shedding
path in `writeStoredComments` stays exactly as it is — screenshots remain the
only thing sacrificed, because they are the only thing that can be
regenerated by taking another one. A log cannot; it _is_ the record.

## Decisions

### The log records four actions, not everything that happens

```js
export const AUDIT_EVENTS = ["created", "edited", "status", "classified"];
```

The requirement asks who _created, changed or resolved_ a comment. That is
creation, a text edit, a status move, and a change of type/priority/tags.

Two things stay out on purpose:

- **Reactions.** High frequency, no audit value. A single triage session can
  toggle a dozen; folding them in would quadruple the log to record that
  somebody clicked 👀.
- **Replies.** A reply already carries its own `author`, `timestamp` and
  `editedAt`, and it is visible in the thread. Copying that into the parent's
  log would be the second place one fact lives.

This bound is what keeps the log at three to five entries per comment instead
of twenty, and it is what makes the quota question above come out the way it
does. It is a decision, not an oversight — recorded as such.

### Identity is persisted, and it is attributive rather than evidential

`authorId` joins `author` on comments and replies: optional, absent by
default, never rendered. The display name stays what gets shown, exactly as
the reactions entry already settled for `user.id`.

What this accepts, and what `DECISIONS.md` has to say out loud: HellDots does
not authenticate anyone. The log records the `user` the host declared at the
moment of the action, and a host can declare anything. The trail is
**attributive** — it says what the application asserted about who acted — not
**evidential**. A deployment that needs the stronger claim gets it by
verifying on its own backend through `onChange`, which carries every mutation
already.

It also puts a little more personal data into `localStorage`, which is the
same concern the reactions entry weighed when it rejected storing
`{ id, name }` per reaction. The difference is that here the requirement asks
for attribution by name, so the data is the point rather than a side effect.

### `schemaVersion` does not move

Both new fields are optional and absent by default, so a corpus written
before this change loads unchanged and simply has no history. That is the
policy `resolvedAt` and `reactions` already follow, and it is why neither
needed a migration. Bumping to `2` would announce a migration path that no
stored payload requires.

A comment resolved before the log existed still renders a duration: the
derivation falls back to the stored `resolvedAt`. It renders `—` only when
there is genuinely nothing to compute from — never an invented figure.

### Resolution time is derived, never stored

`resolutionsOf(comment)` walks the log; `currentResolutionMs(comment)`
returns the elapsed time of the resolution in force, or `null`. Neither is
serialized.

Storing the figure would put the same fact in two places and let it go stale
the moment a comment is reopened — the failure the repo already named in
"Card density, round two: one fact, one place". `resolvedAt` stays exactly as
it is, both for backward compatibility and as the fallback above.

### Clocks belong to the client, so durations are clamped

Every timestamp here is `new Date().toISOString()` on the user's machine.
Merge two devices with skewed clocks — which a host syncing through a backend
will eventually do — and a resolution can land before the creation it
resolves. Durations are clamped at `0` rather than rendered negative, and the
limitation is documented rather than papered over. It matters more once
averages are built on top of these figures in the metrics chunk.

### No new change event

Reactions got a dedicated `reaction:toggled` because a reaction could change
without any other event firing. An audit entry cannot: it is appended _by_
the mutation that already emits `comment:created`, `comment:edited`,
`comment:status-changed` or `comment:updated`, and the serialized comment
those events carry now includes the log. A host subscribing today receives
the history with no new wiring and no new callback to document.

## What the metrics chunk will ask of this log

Written down now so the event shape is not frozen blind to its first
consumer:

| Metric                             | Reads                                          |
| ---------------------------------- | ---------------------------------------------- |
| counts by status / type / priority | current comment fields, not the log            |
| temporal distribution              | `createdAt`                                    |
| average resolution time            | `currentResolutionMs` across resolved comments |
| reopen rate                        | count of `status` entries leaving `resolved`   |
| activity by actor                  | `actor.id ?? actor.name` across entries        |

All five fall out of `{ type, at, actor, from, to }` with no reconstruction
pass. Nothing in the metrics chunk should need the event shape to change.

## Data model

```ts
export interface AuditActor {
  /** From `user.id`, when the host supplies one. Never rendered. */
  id?: string;
  /** The display name at the time of the action. */
  name: string;
}

export type AuditEventType = "created" | "edited" | "status" | "classified";

export interface AuditEvent {
  type: AuditEventType;
  /** ISO timestamp, from the client's clock — see the clamping note. */
  at: string;
  actor: AuditActor;
  /** "classified" only: which field moved. */
  field?: "type" | "priority" | "tags";
  /** "status" and "classified": previous and new value. */
  from?: string | null;
  to?: string | null;
}
```

`Comment` and `SerializedComment` gain:

```ts
authorId?: string | null;
history?: AuditEvent[] | null;
```

`CommentReply` gains `authorId` only — no log, per the decision above.

Rules, matching how `reactions` behaves:

- The serializer emits `history` only when at least one entry exists, so an
  untouched corpus grows by zero bytes.
- Entries are copied out on serialization, actor included, so a host mutating
  the output cannot reach back into overlay state.
- A no-op mutation appends nothing. `setCommentStatus` already returns early
  when the status is unchanged; the recording call goes **after** that guard,
  never before.

`loadComments` normalises defensively, at the same level as the existing
malformed-reply filter and `normalizeReactions`:

- drop entries whose `type` is outside `AUDIT_EVENTS`
- drop entries whose `at` does not parse as a date — an unparseable timestamp
  poisons every average built on top of it
- drop a `field` outside `type | priority | tags`
- coerce the actor to `{ id?, name }`, trimming and capping both at 64 chars
- sort chronologically, because a host merging two devices' corpora can hand
  us an interleaving
- return `null` rather than `[]` when nothing survives

## Components

### `src/audit.js` (new)

```js
actorOf(user, strings); // → { id?, name }
recordEvent(comment, type, actor, detail); // → the entry, or null
normalizeHistory(raw); // → AuditEvent[] | null
serializeHistory(history); // → AuditEvent[] | null
resolutionsOf(comment); // → [{ resolvedAt, reopenedAt, ms }]
currentResolutionMs(comment); // → number | null
```

`actorOf` is to the log what `actorKeyOf` is to reactions: the single place
the question "who is acting" is answered, so the log and the author line can
never disagree. It sits beside `actorKeyOf` rather than replacing it — one
produces a key for de-duplication, the other a record for display.

### `src/audit-timeline.js` (new)

```js
createAuditTrail(comment, { strings, locale, open, onToggle });
```

A disclosure, closed by default, built on the pattern the context block
already established (`DECISIONS.md`, "The inbox's context block is a
disclosure too"). Returns `null` for a comment with no history, so an older
corpus shows nothing rather than an empty box.

Entries render newest first — the question a trail answers is almost always
"what just happened", not "how did this start". Each row is action, actor
name and timestamp; the actor's **id is never rendered**, following the same
rule the reaction pills follow.

Labels reuse `statusLabelOf`, `typeLabelOf` and `priorityLabelOf` from
`comment-actions.js`. No second dictionary: a status must read the same word
in the picker and in the trail.

The previous-resolutions list appears only when there is more than one
resolution. A comment resolved once already shows its elapsed time in the
badge strip, and repeating it under the trail would be a third place for one
fact.

### Surfaces

| Surface        | Trail           |
| -------------- | --------------- |
| Inbox detail   | full disclosure |
| Inbox card     | nothing         |
| Thread popover | nothing         |

The card is at its density limit already — header, four controls, text,
badges, reactions, replies link. The popover is a conversation view; an audit
trail is a triage artifact and belongs where triage happens.

## Refresh hazards

1. **The disclosure's open state lives on the inbox, not in the DOM.** The
   detail is rebuilt on every `refresh()`, and this panel re-renders from ten
   places. One flag for the panel — `this.auditExpanded`, beside
   `this.contextExpanded` — not one per comment, so it stays folded while
   stepping through comments.
2. **`_cardFingerprint()` needs the history in it** if anything the card
   renders derives from the log. The resolution badge does. Without a new
   entry the cached card node is reused verbatim and the badge freezes; the
   cheap entry is the log's length plus its last `at`, not the whole array.
3. **Record after the no-op guard, not before.** `setCommentStatus` returns
   early for an unchanged status; an entry appended above that line would log
   a change that never happened and reset the resolution clock.

## i18n

Nine keys, in both `src/locales/en.js` and `src/locales/es.js`:

| key                        | en                   | es                      |
| -------------------------- | -------------------- | ----------------------- |
| `auditToggleTemplate`      | History ({n})        | Historial ({n})         |
| `auditTrailLabel`          | Activity history     | Historial de actividad  |
| `auditCreated`             | Created the comment  | Creó el comentario      |
| `auditEdited`              | Edited the text      | Editó el texto          |
| `auditStatusTemplate`      | Status: {n}          | Estado: {n}             |
| `auditClassifiedTemplate`  | Changed {n}          | Cambió {n}              |
| `auditFieldTags`           | tags                 | las etiquetas           |
| `auditPreviousResolutions` | Previous resolutions | Resoluciones anteriores |
| `auditResolvedInTemplate`  | Resolved in {n}      | Resuelto en {n}         |

`auditStatusTemplate` receives an already-composed `Open → Resolved`, and
`auditClassifiedTemplate` receives `typeLabel` / `priorityLabel` /
`auditFieldTags`. Only tags needs a key of its own — the other two labels
already exist. `formatTemplate` substitutes a string, which is what it
already does for the duration badges, so no plural forms are involved.

## Testing

New `test/audit.test.js`:

- `recordEvent` rejects an unknown type and appends nothing
- `actorOf` prefers `user.id`, falls back to the name, then to anonymous;
  trims and caps both fields
- `normalizeHistory` drops unknown types, unparseable dates, bad `field`
  values and non-string actors; sorts an interleaved array; returns `null`
  when nothing survives
- `resolutionsOf` returns one interval per resolve/reopen pair, leaves the
  last one open when the comment is still resolved, and clamps a resolution
  that predates its own creation to `0`
- `currentResolutionMs` returns `null` when not resolved, and falls back to
  `resolvedAt` for a comment with no log

New `test/audit-timeline.test.js`:

- `null` for a comment with no history
- rows are newest first
- the actor's id never appears in the rendered output
- previous resolutions render only when there is more than one
- the toggle carries `aria-expanded` and hides the body

Additions to existing suites:

- `overlay.test.js` — a no-op `setCommentStatus` appends nothing; a resolve →
  reopen → resolve cycle leaves two entries and one open resolution;
  `authorId` is stamped from `user.id` on both creation paths
- `persistence.test.js` — round-trip; an empty log is omitted entirely;
  normalisation runs on load; a corpus with no `history` loads unchanged and
  still renders its `resolvedAt` duration
- `inbox.test.js` — the fingerprint changes when the log grows; the
  disclosure's open state survives a `refresh()`
- `i18n.test.js` — key parity across both locales, and the hardcoded-English
  scanner stays green for the two new modules

Focus rings are deliberately not added — the known, documented gap.

## Out of scope

Filtering or sorting the inbox by anything in the log; an actor's own view
("everything I changed"); reply and reaction events; server-side verification
of attribution; exporting the trail (the metrics chunk owns exports); a cap
or retention policy on the log, which the measured payload does not justify.
